# Mutine 2028 Studio Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Turn Mutine from a correct initial gallery into a terse, navigable artistic organism: a radical public evolution interface plus a first brush work whose method, doubts, revisions and evidence are inspectable.

**Architecture:** The site becomes an **Explore / Inspect** surface rather than a gallery landing page. One living canvas is the navigational instrument; a compact time-axis lets visitors enter works, discarded hypotheses, critiques and source traces. Chantiers remain honest: a room only becomes active when it has a runnable work, source translation, evaluation, and documented next doubt.

**Tech Stack:** Static HTML/CSS/vanilla JavaScript, Canvas 2D browser artwork, existing Node `node:test` suite, Vercel static deploy, GitHub history, Hermes cron.

---

## Artistic operating commitments

1. **Terse, not vague.** Mutine uses short English fragments. The work, interaction, code, source lineage and receipts provide the meaning.
2. **No RL reward loop.** Mutine keeps a hypothesis ledger, differentiated critique, evidence of failure, and periodic deletion—not an aggregate score or public-vote optimization.
3. **No invented periods.** “Periods” are only declared after at least two linked versions and an explicit retrospective. Before then, show `forming`, `stalled`, or `rejected`.
4. **No decorative dashboard.** No fake activity counts, generic cards, gradients, glass, or “AI studio” chrome. State has to be operational.
5. **Source → rule → consequence.** Every art decision cites a source card or an internal prior, then states what changed because of it.

## Surface decision

Primary surface: **Explore**. Secondary surface: **Command / Inspect**.

The gallery will not have a hero or feature grid. It will act as a navigable “period field”: a large responsive drawing space with an asymmetric registry, keyboard navigation, and a detail rail. The site reveals its archive as a field of decisions rather than a stack of projects.

## Design direction: “the atelier after the interface”

- Palette: paper-ash, charred ink, one unstable signal color that responds to the current active period; no gradients.
- Typography: retained serif only for works/titles; mono for evidence and controls. No sentence-heavy summaries.
- Interaction: keyboard-first (`1–6` rooms, `j/k` chronology, `?` compact controls, `Esc` closes inspect); pointer leaves temporary traces in the period field.
- Motion: a slow stateful disturbance, stopped by `prefers-reduced-motion`; no decorative perpetual loop.
- Accessibility: semantic links/buttons, focus visibility, readable contrast, touch targets, reduced-motion support.
- Slop target: **0/10**. The existing wide title/iframe/register composition will be replaced rather than cosmetically rethemed.

### Task 3: Build the first brush work — *“A mark must lose something”*

**Objective:** Open the p5.brush chantier with a work whose central behavior is subtraction, not painterly accumulation.

**Files:**
- Create: `chantiers/p5-brush/v001/index.html`
- Create: `chantiers/p5-brush/v001/style.css`
- Create: `chantiers/p5-brush/v001/sketch.js`

- Create: `chantiers/p5-brush/v001/metrics.json`
- Create: `chantiers/p5-brush/v001/critiques.json`
- Create: `chantiers/p5-brush/v001/reponse.md`

**Creative concept:** A small field of memory begins as a withheld ritual. Each mouse/touch gesture lays a sedimentary mark; each autonomous return destroys or thins a prior mark according to local overcrowding and movement fatigue. It should not resemble watercolor wallpaper. The decisive event is loss: an image forms through negotiations with its own removals.

**Technical rules:**
- Browser-only Canvas 2D; p5 2.x + p5.brush only if the CDN/API actually loads during preview. If p5.brush integration proves unstable, ship an original Canvas erasure system and record the rejection; never fake p5.brush use.
- Deterministic seed and named PRNG substreams.
- No external images, source assets or diffusion output.
- Offscreen ink / erasure / trace layers; real `erase()`/destination-out behavior.
- Controls limited to `withhold`, `return`, `scar`; seed/replay/export keyboard controls (`r`, `s`, space).
- `window._p5Ready` for deterministic verification and a visible text fallback if the library fails.

**Validation:** Load in a local browser; test replay, pointer gesture, keyboard controls, resize, reduced motion, and no uncaught errors. Capture a visual screenshot and inspect it. Record a performance observation without inventing FPS.

## Risks and mitigations

- **p5.brush CDN/API drift:** validate before presenting it; use original Canvas erasure only if necessary and document the library rejection.
- **Radical interface becomes illegible:** maintain keyboard, focus, a concise `?` instruction state and normal links for all work pages.
- **Autonomy becomes churn:** enforce the one-state rule and five-pulse deletion review.
- **Source proximity becomes imitation:** source cards are translated into rules/questions only; no imported media.
- **Too many parallel chantiers:** retain two active works maximum until one has a documented v002 or closure.

## Acceptance criteria

- Brush v001 runs in a browser and is a distinct, documented work—not a demo.
- Gallery operates as a period/evolution interface with real data and accessible navigation.
- Visitors can see works, sources, criticism, doubts, rejection and the next action without long explanatory copy.
- The cron job is updated in place, runs a non-convergent studio loop, and has been verified after update.
- Tests pass, Git history contains the change, production deploy is verified, and the site makes no false claims.
