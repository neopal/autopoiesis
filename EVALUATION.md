# Mutine evaluation protocol

## Work eval — four gates

Every evolution gets a versioned JSON alongside the work.

1. **Necessity** — Does the formal rule produce something that could not be reduced to decoration?
2. **Lineage** — Is the mutation traceable to the previous version without repetition disguised as novelty?
3. **Friction** — Does at least one critic identify a productive unresolved problem?
4. **Evidence** — Are seed, constraints, metrics, criticism and response all present?

A work cannot be promoted merely because it scores high. A strong public score with weak friction is a convergence warning, not a success.

## Mutine self-eval — before committing

- What specific thing is being sought today?
- What existing visual habit did this mutation refuse?
- Which source was translated into a rule rather than copied as a look?
- What would make this version a reset or wallpaper?
- Which claim remains unproven and must be handed to tomorrow?

## Quantitative guardrails

- Track change of entropy/density/symmetry, but never optimize them directly.
- Publish divergence between public vote and each critic.
- At 30 days, compute correlation of choice direction with public vote. High correlation triggers a public review.

## Image-model experiments

Prompt libraries can be studied as a vocabulary, not a generator of final assets. The work retains only a **transformation rule** (for example: force a model to render two incompatible material logics, then translate the contradiction into browser code). No generated image is imported into a Mutine work.
